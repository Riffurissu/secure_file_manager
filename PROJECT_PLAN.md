# План и состояние проекта FileManager

## 1. Исходные задания

Проект объединяет два связанных учебных задания:

1. Защищённый файловый менеджер с базой данных.
2. Локальный CI/CD-конвейер с Docker, тестами, SAST, кэшированием и артефактами.

Приложение сначала должно работать самостоятельно. CI/CD добавляется после завершения основной функциональности.

## 2. Принятые решения

### Технологии

- Язык: C#.
- Платформа: .NET 8 (`net8.0`).
- API: ASP.NET Core Minimal API.
- Интерфейс: HTTP API; проверка и демонстрация выполняются через `curl` (примеры в `README.md`).
- База данных: SQLite через `Microsoft.Data.Sqlite` 8.0.11.
- Тесты: xUnit, `Microsoft.AspNetCore.Mvc.Testing`, coverlet.
- Целевая среда запуска: Linux-контейнер (Docker). Код должен работать и в Windows для разработки.
- Будущий CI: GitLab CI с Docker-раннером.

### Почему сервер, а не консольное приложение

Консольное приложение не имеет порта для проброса в Docker. Поэтому приложение реализуется как HTTP-сервер, который можно запускать локально и в контейнере.

### Структура проектов

```text
FileManager/

├── .dockerignore

├── PROJECT_PLAN.md

│   ├── Files/       пути, файловый сервис, лимиты

│   ├── Structured/  JSON и XML
│   └── System/      диски

```

Папка `GitLab` в каталоге практики предназначена для будущей CI/CD-фазы и текущим приложением не изменяется.

### SQLite

SQLite выбран для отсутствия отдельного сервера БД. Файл базы данных создаётся приложением автоматически. Используются:

- `PRAGMA foreign_keys = ON`;
- `PRAGMA busy_timeout = 5000`;
- `PRAGMA journal_mode = WAL`.

В SQLite нет `SERIAL`, `ENUM` и хранимых процедур. Поэтому используются `INTEGER PRIMARY KEY AUTOINCREMENT`, `TEXT` с `CHECK`, а доступ к БД реализован параметризованными методами репозиториев.

### Аутентификация

Капча не используется. Защита от перебора строится на:

- PBKDF2-SHA256 с 600 000 итерациями и уникальной солью;
- сравнении хешей через `CryptographicOperations.FixedTimeEquals`;
- временной блокировке после неудачных входов (5 неудач: 1 минута, затем 5 минут);
- ограничении частоты `/api/auth/login` по IP: 10 запросов в минуту;
- одинаковом ответе для неверного пароля, неизвестного пользователя и заблокированного аккаунта;
- журналировании попыток входа в SQLite.

IP-ограничение дополняет, но не заменяет блокировку аккаунта. Оно не защищает от распределённой атаки и может затронуть пользователей за общим NAT.

### Токены

После успешного входа выдаётся случайный bearer-токен сроком на один час. В БД хранится только SHA-256 токена.

### Домашняя директория

Каждый пользователь работает только в `storage/<username>/`. Папка создаётся при регистрации. Выход за её пределы, абсолютные пути и обход через `..` запрещены.

### Пути и файловая система

- Запрещённые символы и зарезервированные имена Windows (`CON`, `NUL`, `COM1-9`, `LPT1-9`) запрещены в любой ОС, чтобы данные оставались переносимыми.
- Симлинки и reparse points проверяются через `LinkTarget` (работает в Linux, в том числе для битых симлинков) и атрибут `ReparsePoint` (для Windows).
- Регистр имён: в Windows не различается (поиск в БД и блокировки без учёта регистра), в Linux различается.

### Лимиты

Все лимиты вынесены в `Files/StorageLimits.cs` и применяются во всех операциях:

| Лимит | Значение | Где применяется |
|---|---|---|
| Размер файла | 10 МБ | запись, чтение, загрузка, JSON/XML-документ, сам ZIP-архив |
| Суммарный распакованный размер на архив | 50 МБ | создание и распаковка архива |
| Записей в архиве | 1000 | создание и распаковка |
| Глубина каталогов и JSON/XML | 32 | обход каталогов, разбор JSON/XML |
| Узлов JSON/XML | 50 000 | разбор JSON/XML |
| Коэффициент сжатия (для записей больше 1 МБ) | 100 | распаковка |
| Попыток входа с одного IP | 10 в минуту | `/api/auth/login` |

### JSON и XML

Минимально доверенная обработка:

- ограничение размера входа (10 МБ, общий лимит файла);
- ограничение глубины (32) и количества узлов (50 000);
- JSON без комментариев и trailing comma, повторяющиеся имена полей отклоняются;
- XML с `DtdProcessing.Prohibit` и `XmlResolver = null`;
- сериализация стандартными библиотеками без ручной конкатенации.

Схемы DTO/allowlist для фиксированных контрактов не введены: в текущем объёме задача их не требует.

### Диски

`GET /api/system/drives` показывает диски того окружения, где запущено приложение. В контейнере это файловые системы контейнера; диски хоста не монтируются (решение пользователя). Виртуальные ФС Linux (`proc`, `sysfs`, `tmpfs`, `overlay` и др.) исключаются.

### Docker

- HEALTHCHECK не используется (решение пользователя).
- Контейнер запускается от непривилегированного пользователя `app`.
- Данные хранятся в томе `/data`.

## 3. Выполнено

Ни сборка, ни тесты после этапа 2 не запускались по указанию пользователя. Весь код проверен только чтением.

### Каркас решения

- Решение `FileManager.sln`, проекты `FileManager.Api` и `FileManager.Tests` в корне.
- Пакеты: `Microsoft.Data.Sqlite` 8.0.11, xUnit, `Microsoft.AspNetCore.Mvc.Testing` 8.0.11, coverlet.

### База данных

- `Data/Database.cs`: соединения, `foreign_keys`, `busy_timeout`, WAL, создание схемы.
- Таблицы: `Users`, `Files` (мягкое удаление через `is_deleted`, уникальный индекс активных файлов по владельцу и пути), `Operations` (CHECK на тип операции), `AuthTokens`, `LoginAttempts`.
- Репозитории: `UserRepository`, `FileRepository`, `LoginAttemptRepository`, `TokenRepository`. Все запросы параметризованы.
- Изменение `Files` и запись в `Operations` выполняются в одной транзакции.
- `FileRepository.ApplyBatch`: пакетная запись журнала одной транзакцией (используется распаковкой ZIP).

### Аутентификация (этап 1)

- `Security/PasswordHasher.cs`, `Auth/LockoutPolicy.cs`, `Auth/AuthService.cs`, `Auth/TokenRepository.cs`, `Auth/BearerAuth.cs`.
- Регистрация, вход, блокировка, bearer-токены, rate limiting входа.
- Эндпоинты: `GET /health`, `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`.

### Безопасный файловый путь (этап 2)

- `Files/SafePathResolver.cs`: относительные пути, нормализация, границы домашней папки, длина, имена, зарезервированные имена, симлинки и reparse points на каждом существующем сегменте.
- `Files/ResolvedPath.cs`, `Files/PathValidationException.cs`.

### CRUD файлов и каталогов (этап 3)

- `Files/FileService.cs`: список каталога (симлинки и временные файлы скрыты), чтение, запись через временный файл с атомарной заменой, мягкое удаление, создание каталога.
- Блокировки по полному пути внутри процесса.
- Аудит: create/modify/delete в `Operations`; создание каталога — отдельная запись без `file_id`.
- Эндпоинты: `GET /api/files`, `GET/PUT /api/files/content`, `DELETE /api/files`, `POST /api/folders`, `GET /api/operations`.

### Сведения о дисках (этап 4)

- `System/DriveService.cs`: `DriveInfo`, фильтр сетевых и оптических дисков, виртуальных ФС Linux, безопасное чтение метки тома.
- Эндпоинт: `GET /api/system/drives`.

### JSON и XML (этап 5)

- `Structured/StructuredData.cs`: нормализация JSON и XML с лимитами и запретами из раздела 2.
- Эндпоинты:
  - `POST /api/structured/validate?format=json|xml`;
  - `POST /api/structured/save?path=&format=`;
  - `GET /api/structured/read?path=&format=`.
- Чтение тела запроса ограничено (`ReadBodyLimitedAsync`).

### ZIP (этап 6)

- `Archive/ZipService.cs`:
  - `Create`: упаковка файла, каталога или всей домашней папки в `.zip`. Сам архив исключается из упаковки. Пустые каталоги сохраняются.
  - `Extract`: атомарная распаковка.
- Атомарность распаковки:
  1. Все записи проверяются до записи на диск: лимит числа записей, Zip Slip через `SafePathResolver`, повторяющиеся пути, заявленный размер, коэффициент сжатия.
  2. Файлы пишутся через `FileService.WriteFileRaw` без журнала; для каждого сохраняется снимок прежнего содержимого. Созданные каталоги фиксируются отдельно.
  3. Журнал записывается одной транзакцией `ApplyBatch` только при полном успехе.
  4. При любой ошибке `Rollback` восстанавливает перезаписанные файлы, удаляет новые файлы и пустые созданные каталоги в обратном порядке. Ошибка одного шага не прерывает остальные.
- Фактический размер распаковки считается потоком, а не по заголовку записи.
- Симлинки из архива не создаются: записи пишутся только как обычные файлы.
- Эндпоинты: `POST /api/archive/create?source=&archive=`, `POST /api/archive/extract?archive=&destination=`.
- Ограничение: откат best-effort. Если файловая система вернёт ошибку при восстановлении, часть изменений может остаться. Транзакционность журнала при этом сохраняется.

### Docker (этап 7)

- `.dockerignore`: исключает `bin`, `obj`, тесты, `storage`, файлы БД, `GitLab`, `PROJECT_PLAN.md`.

### Документация

Места, которые нужно проверить при первом запуске:

- `Zip_bomb_by_declared_size_is_rejected` ожидает `413`; срабатывает либо заявленный размер в `PlanExtraction`, либо фактический в `ReadEntryLimited`, оба дают 413.

- `Deep_nested_json_is_rejected` проверяет только `NotEqual(OK)`.

- `ZipService.Collect` сравнивает пути без учёта регистра при исключении архива из упаковки; на Linux это может исключить файл, отличающийся регистром.

## 6. Условия и оговорки

- Не создавать и не изменять папку `GitLab` до этапа CI/CD.
- Не создавать `.gitignore`, пока это отдельно не согласовано.
- Не выполнять `git init` и не создавать коммиты без отдельного указания.
- Не запускать сборку и тесты без отдельного согласования.
- Перед каждым крупным этапом сначала предоставлять план на одобрение.
- Успешная сборка не подтверждает безопасность; нужны тесты и проверка в контейнере.
- SQLite подходит для учебного локального проекта, но не для высоконагруженного многопользовательского сервиса.
- Rate limiting по IP — дополнительная защита, а не замена блокировке аккаунта.
- Мягкое удаление сохраняет записи для аудита и позволяет повторно создать файл с тем же путём.
- Все внешние данные (пути, JSON, XML, ZIP) считаются недоверенными.
- Docker используется для запуска приложения; CI/CD подключается после этого.
